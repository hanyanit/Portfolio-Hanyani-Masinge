# Sprint Backlog — Opportunity Connect

## 1. Introduction

The Sprint Backlog contains the items selected from the Product Backlog for development during a specific sprint.

For Opportunity Connect, the Sprint Backlog was used to break selected user stories into smaller development tasks. This made it easier to plan the work, track progress and focus on delivering usable functionality within the sprint.

The sprint focused on developing and improving the core functionality that allows students to discover and access bursaries and other opportunities.

---

## 2. Sprint Goal

### Sprint Goal

> To develop and improve the core Opportunity Connect functionality that allows students to access, search for and discover relevant opportunities.

The sprint goal provided a clear direction for the development work and helped ensure that the selected tasks contributed to the main purpose of the application.

## 4. Sprint Task Breakdown

### User Registration

The registration user story was divided into smaller technical tasks:

- Design the registration form.
- Add the required input fields.
- Add form validation.
- Connect the Angular frontend to the Python backend.
- Send registration information to the backend.
- Handle successful registration.
- Handle registration errors.
- Test the registration process.

### User Login

The login functionality was divided into:

- Design the login interface.
- Add email/username and password fields.
- Validate login information.
- Connect the frontend to the backend.
- Process the login request.
- Handle successful authentication.
- Display appropriate error messages.
- Test the login process.

### Opportunity Discovery

The opportunity-discovery functionality was divided into:

- Create the opportunity listing.
- Retrieve opportunity information from the backend.
- Display opportunity information.
- Create search functionality.
- Implement filtering.
- Display detailed opportunity information.
- Test search and filtering functionality.

---

## 5. Sprint Progress

Progress was monitored throughout the sprint by tracking the status of each task.

The tasks could be grouped into the following stages:

### To Do

Tasks that had not yet been started.

### In Progress

Tasks that were currently being developed or tested.

### Done

Tasks that had been completed and tested.

This approach helped provide visibility into the development process and made it easier to identify work that still needed attention.

---

## 6. Definition of Done

A Sprint Backlog item was considered complete when:

- The required functionality had been implemented.
- The frontend and backend integration worked where applicable.
- The feature had been tested.
- Major errors had been addressed.
- The feature worked according to the relevant user story.
- The completed work could be demonstrated.

The Definition of Done helped maintain a consistent standard for completed work.

## 8. Reflection

Creating the Sprint Backlog helped me understand how Agile development can be used to organise work into smaller and more manageable development cycles.

The Product Backlog contained the broader requirements for Opportunity Connect, while the Sprint Backlog allowed me to select specific items that could be worked on during the sprint. Breaking the user stories into smaller technical tasks made the development process easier to manage.

For example, the requirement to allow students to search for opportunities was broken into smaller tasks such as creating the search interface, connecting it to the opportunity data and testing the search functionality. This helped me focus on completing smaller pieces of work rather than treating the entire feature as one large task.

The Sprint Backlog also helped me track progress and identify which tasks were completed, in progress or still outstanding. This provided better visibility of the development process.

One of the main lessons I learned was that effective sprint planning requires realistic task selection. Selecting too much work can make it difficult to complete the sprint, while selecting too little may result in the team not making enough progress.

Overall, the Sprint Backlog improved my understanding of sprint planning, task breakdown, prioritisation and incremental software development.

---

## 9. Conclusion

The Sprint Backlog provided a structured plan for the development work completed during the sprint. It connected the Product Backlog and User Stories to specific development tasks and helped maintain focus on delivering useful functionality for Opportunity Connect.

Using a Sprint Backlog demonstrated how Agile practices can be applied to an actual software development project rather than only being understood as theoretical concepts.
